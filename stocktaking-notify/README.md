# stocktaking-notify · 资产盘点通知引擎

> 一个把"**什么时候该发、发给谁、一天最多发几条、发失败怎么办**"全部收口到一个入口的盘点通知引擎。
> 核心逻辑零运行时依赖（仅 SLF4J），可直接嵌入现有 Spring / RuoYi / 自研系统。

## 这是什么

企业内部资产盘点通常长这样：**财务发起一期盘点计划 → 责任人去盘自己名下的资产 → 到期前反复催办**。
通知这件事看起来简单，真做起来会踩一连串坑：

| 常见事故 | 后果 |
|---|---|
| 计划还没开始 / 已经过期，却因为"状态被改成进行中"而群发 | 范围外打扰，责任人质疑系统 |
| 节假日 16:45 定时任务照常催办 | 打扰假期，投诉 |
| 收件人按姓名匹配账号，遇到同名 | **把通知发给了非责任人** |
| 责任人明明盘完了，还在天天被催"还有 X 项未盘点" | 盘点结果写到别的计划期次上去了 |
| 开始通知 + 每日提醒 + 多期计划各发一条 | 一天收到好几条，变成骚扰 |
| 企微接口偶发失败 / 名单里有一个离职账号 | 要么整批收不到，要么谁都不知道没发出去 |

本项目把这些规则**显式建模成一条闸门链**，并提供完整的可观测性（每个节点都有统一标识的日志与结构化结果）。

## 核心特性

- **闸门链**：`状态 → 节假日(START豁免) → 时间窗 → 本次清单(含接收权限过滤) → 收件人资格 → 一天一条 → 发送`，任一不过即不发。
- **一人一天一条**：限流键维度只到「人 + 自然日」，**跨通知类型、跨计划**共用同一把锁（开始通知与提醒不会叠加）。
- **只发给资产责任人本人**：收件人只取本次计划清单，账号只按用户ID精确匹配，**不做姓名兜底**。
- **接收权限点闸门（"权限点存在即启用"）**：只有持有接收权限的角色成员才进入收件人清单；
  "只发给个别人"= 在角色管理里按需勾选，**无任何参数开关**（v1.1.0 起取代测试模式）。
- **按文案分组群发**：同文案的人合并为一次调用（接收人 `|` 分隔，单次上限 1000 自动分片），
  200 人从"1~2 分钟"降到"十几秒"；回执带出坏账号时**剔除后重发**，不让一个坏账号拖垮整批。
- **免登录深链文案（2026-09-28 定稿）**：消息内嵌企微 OAuth 深链，员工点击即免登录进入系统；
  三种文案（开始/提醒/最后一天）经基准测试逐字钉死。
- **演练模式**：只做只读判定与文案预览，**不占限流键、不发送**，且会告诉你"今天这个人还会不会被发到"。
- **全链路可观测**：统一节点标识 `GATE-STATUS / GATE-HOLIDAY / GATE-WINDOW / GATE-LIST / RECEIVE-PERM / BENEFICIARY / DAY-LIMIT`，
  日志、返回结果、文档三处互相对照，出问题不需要猜。
- **零运行时依赖**：核心只依赖 SLF4J；企微发送、Redis、数据库全部通过 3 个扩展点接入。

## 设计原则

> **宁可不通知，也不要乱通知。**

1. 判断不出来 → **不发**（没有截止时间、清单为空、状态不是进行中）。
2. 定位不到责任人账号 → **不发**（不做姓名/模糊兜底，宁可漏发也不发给非责任人）。
3. 真实发送 → **没有任何绕过开关**（时间窗、节假日、状态在发送链路内部强制生效）。
4. 发送失败 → **释放限流键**，允许当天重跑补发，而不是"这个人今天彻底收不到"。
5. 同一人同一天 → **只发一条**（多期计划并行、开始通知与提醒叠加，都不会变成骚扰）。

## 闸门链

```
                      ┌─────────────────── 计划级（整批） ───────────────────┐
 触发源 ──────────▶ ①GATE-STATUS ─▶ ②GATE-HOLIDAY ─▶ ③GATE-WINDOW ─▶ ④GATE-LIST
 （改状态/定时/诊断）  状态=进行中      节假日与周末     开始~截止之间      本次清单取数
                      └──────────────────────────────────────────────────────┘        （含接收权限过滤）
                                            │ 全部通过
                                            ▼
                      ┌─────────────────── 逐人 ───────────────────┐
                     ⑤BENEFICIARY（有待盘点 + 有企微号） ─▶ ⑥DAY-LIMIT（一人一天一条）
                      └────────────────────────────────────────────┘
                                            │ 占位成功
                                            ▼
                      按「相同文案」分组 ─▶ 分片（≤1000人）─▶ 群发 ─▶ 坏账号剔除重发
                                            │
                                            ▼
                                  SUMMARY（发送/跳过/失败/演练）
```

各节点的判定条件、失败原因与对应日志见 [`docs/02-架构与闸门链路.md`](docs/02-架构与闸门链路.md)。

## 快速开始

### 环境要求

- JDK 8+（已在 JDK 17 上验证编译与测试）
- Maven 3.6+

### 跑测试（含可执行演示）

```bash
mvn test
```

预期输出：`Tests run: 46, Failures: 0, Errors: 0`，并且能看到演示用例打印出的整条闸门链路日志。

想直接看「评审修复逐项验收报告」（可截图当验收证据）：

```bash
mvn test -Dtest=ReviewAcceptanceTest
```

### 5 行代码接入

```java
StocktakingNotifyService engine = StocktakingNotifyService.builder()
        .respUserProvider(myRespUserProvider)        // 收件人数据源（按 planId 查本次清单；在此实现接收权限过滤）
        .messageSender(myWeChatMessageSender)        // 消息发送器（支持一次发多人）
        .dailyLimitStore(myRedisDailyLimitStore)     // 一天一条限流存储（SET NX EX）
        .build();

// 计划状态改为「进行中」时
engine.sendStartedNotify(plan, LocalDate.now());

// 每天 16:45 定时任务
engine.sendDailyRemind(plan, LocalDate.now());

// 运维诊断（dryRun=true 只预览不发送）
List<NotifyResult> preview = engine.notify(plan, NotifyType.REMIND, LocalDate.now(), true);
```

返回的 `List<NotifyResult>` 就是"每个人的判定结果"，可直接落库、输出到接口或打印成表格：

| 字段 | 含义 |
|---|---|
| `decision` | `SEND` / `SKIP` / `FAIL` / `PREVIEW` |
| `gateNode` | 被哪道闸门拦下（整批或逐人） |
| `reason` | 为什么拦下 / 失败原因（可直接给运维看） |
| `content` | 实际发送（或预览）的文案 |

测试覆盖的承诺（每条都有断言守着）：

- 同文案只调用一次发送接口（分组群发生效）
- 状态不是进行中 / 节假日 / 未开始 / 已过期 → 整批不发；**开始通知豁免节假日**（周末改状态不会永久丢失）
- 已盘完的人、没有企微号的人 → 单独跳过，其余人照发
- 同一人同一天第二次发送被跳过，且**不再调用发送接口**（含开始通知，一天一条是硬承诺）
- **发送接口抛异常**：整批判失败、释放限流键、异常不冒泡到调用方
- **发送环节崩溃不会被统计成"跳过"**（PENDING 独立状态，汇总按失败计）
- **三种文案逐字钉死**（2026-09-28 定稿：免登录深链 + 「鼎勤信息管理」/「个人盘点清单」命名 + 初次登录提示）
- **GATE-ROLE 角色过滤**：只发给配置角色的成员，其余人跳过并写明原因
- **发送留痕落库**：真实执行落库、演练不落、落库故障不影响发送
- 坏账号从名单剔除后重发成功；与账号无关的失败整批判失败并释放限流键

## 常见问题

**Q：为什么要"一天一条"这么严？多期计划并行时怎么办？**
A：真实业务里，"开始通知 + 16:45 提醒 + 多期计划"叠加会让同一个人一天收到好几条，很快就变成骚扰。
限流键刻意只到「人 + 自然日」，因此当天先发出去哪一条，后面的全部跳过。
更彻底的做法是**从源头禁止多期并行**（同一时段只允许一个进行中计划），本项目不负责该约束，
但在 `docs/02` 里说明了为什么它同样重要。

**Q：为什么收件人不做"按姓名匹配账号"的兜底？**
A：同名时会匹配到另一个人 —— 这等于把资产盘点通知发给了非责任人，比漏发严重得多。
正确做法是推动业务把责任人的用户ID补全（参考 SQL 会把这类资产统计出来）。

**Q：企微一次能发多少人？**
A：文本消息的接收人用 `|` 分隔，单次最多 1000 个。本项目按 1000 自动分片，
因此既不会超限，也不需要接入方自己切分。

**Q：能换成钉钉 / 邮件 / 短信吗？**
A：可以。实现 `MessageSender` 即可，其余逻辑完全复用（"按文案分组群发"要求你的渠道支持一次发多人）。

# 05 · 真实测试方案（傻瓜版）

> 目标：让你在**没有任何前置知识**的情况下，从"一条命令跑通"到"真实企微沙箱发消息"再到"生产灰度"，
> 每一步都知道**敲什么、看什么、什么算通过、不通过怎么办**。
>
> 全文按 5 个阶段递进，每个阶段都能单独停、单独验收：

| 阶段 | 环境 | 验证什么 | 耗时 | 谁能做 |
|---|---|---|---|---|
| S0 单元测试 | 本机 | 代码逻辑没被改坏（34 条已有 + 12 条验收） | 30 秒 | 任何人 |
| S1 验收脚本 | 本机 | 本次代码评审的 12 项修复逐条生效 | 30 秒 | 任何人 |
| S2 沙箱真发 | 企微测试应用 | 真能发出去、发失败会自愈、留痕能查到 | 1 小时 | 有企微管理员权限 |
| S3 脏数据演练 | 沙箱 | 坏账号/重复号/已盘完/无企微号不炸 | 1 小时 | 同上 |
| S4 生产灰度 | 生产 | 真实用户 1→全体放量，可回滚 | 1 天 | 运维 + 业务 |

## 0. 五分钟跑通（先建立信心）

**第 1 步**：打开命令行（Windows 用 PowerShell），进入项目目录：

```powershell
cd C:\Users\Chg10\Desktop\stocktaking-notify
```

**第 2 步**：敲这一条命令，回车：

```powershell
mvn test
```

**第 3 步**：等 30 秒左右，看到最后几行出现这两个关键字就算通过：

```
[INFO] Tests run: 46, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

**怎么判断失败**：只要出现 `BUILD FAILURE` 或 `Failures` / `Errors` 不是 0，就是没通过。
往上翻，找到第一行 `<<< FAILURE!` 或 `<<< ERROR!`，它下面会直接写"哪个测试、期望什么、实际什么"。

> 注意：日志里出现 `ERROR` 开头的行**不一定是坏事**。很多测试就是故意制造错误（比如模拟企微超时），
> 那些 ERROR 日志是"被测对象正常工作"的证据。**只认最后那行 `Failures: 0, Errors: 0`。**

## 2. S1：验收脚本（本次评审 12 项修复逐条生效）

```powershell
mvn test -Dtest=ReviewAcceptanceTest
```

这个类**不是普通单测**，它会把每一项修复的"现象 → 预期 → 实际 → 结论"打印成一张表，
可以直接截图发群里当验收证据。预期输出长这样（节选）：

```
================ 盘点通知引擎 · 评审修复验收报告 ================
【P0-1】发送环节崩溃不冒充"跳过"            ...... 通过  失败=2 跳过=0
【P0-2】发送接口抛异常不冒泡、限流键已释放    ...... 通过  异常未抛出，键=0 个
【P1-3】测试模式配置写错一律 fail-closed     ...... 通过  调用发送接口 0 次
...
================ 结论：12/12 项通过 ================
```

**通过标准**：末行 `12/12 项通过` + `BUILD SUCCESS`。

**逐项对照表**（评审编号 → 现象 → 预期）：

| 编号 | 评审问题 | 本脚本怎么验 | 预期现象 |
|---|---|---|---|
| P0-1 | pending 复用 SKIP，发送崩了被记成"跳过" | 让发送器抛异常，看汇总 | `失败=2 跳过=0`（不再谎报跳过） |
| P0-2 | 发送异常未兜住 → 限流键泄漏 + 调用方拿到异常 | 让发送器抛异常，看键 + 看有没有抛出 | 不抛异常；`store.occupiedKeys()` 为空（可当天补发） |
| P1-4 | 周末改状态 → 开始通知永久丢失 | 把今天设为节假日，发开始通知 | 开始通知照发；同一天的提醒仍被拦 |
| P2-6 | 空清单提示漏了"已盘完" | 清单返回空，看 reason | 文案含"或全部资产已盘完" |
| P2-7 | 成功计数用未去重的 size，统计虚高 | 两个人配同一个企微号 | 只调用 1 次、只发给 1 个号 |
| P2-8 | dispatch 返回值无人用，两套统计口径 | 编译期已保证（返回 void） | 代码里无法再拿到第二套统计 |
| 角色闸门 | 只能靠 SQL 过滤角色 | 两个不同角色的人 + `notifyRoles` | 只发命中角色，另一人 `GATE-ROLE` 跳过 |
| 留痕落库 | 线上答不出"这人到底收到没有" | 接一个内存留痕库再发一次 | 每人一条留痕；演练不落；留痕故障不影响发送 |
| 一天一条 | START 能否插队（业务拍板：不能） | 提醒先发，再发开始通知 | 开始通知被 `DAY-LIMIT` 拦下，只调用 1 次 |
| 测试模式解析 | 配置顺序写错 → 静默发全员 | 配置改成"键顺序打乱""大小写不一致""值非法" | 乱序/大小写能识别；值非法 = 一条不发 |

## 3. S2：沙箱真发（1 小时，第一次接真实企微必做）

### 3.1 准备清单（缺一不可）

| 要准备的东西 | 从哪拿 | 用来干什么 |
|---|---|---|
| 企微「自建应用」的 `corpid` / `agentid` / `secret` | 企微管理后台 → 应用管理 → 自建应用 | 发消息要鉴权 |
| 你自己的企微账号（工号） | 企微手机端 → 我 → 账号 | 当白名单，先只发给自己 |
| Redis 地址 | 问运维 | 存"一天一条"占位键 |
| 数据库账号 | 问运维 | 落发送留痕 |
| 一个进行中的盘点计划 ID | 系统里随便建一个测试计划 | 当输入参数 |

### 3.2 写 4 个实现类（引擎只认接口，不认框架）

**① 消息发送器** —— 最容易踩坑的一个：

```java
public class WeComMessageSender implements MessageSender {
    @Override
    public SendReceipt send(List<String> webComIds, String content) {
        try {
            String touser = String.join("|", webComIds);   // 企微要求 | 分隔
            String url = "https://qyapi.weixin.qq.com/cgi-bin/message/send?access_token=" + token();
            String body = "{\"touser\":\"" + touser + "\",\"msgtype\":\"text\",\"agentid\":" + AGENT_ID
                    + ",\"text\":{\"content\":\"" + content.replace("\"", "'") + "\"}}";
            // 发 POST，解析 JSON 里的 errcode / errmsg / invaliduser / unlicenseduser
            if (errcode == 0) {
                return SendReceipt.success();
            }
            // 关键：把不可用账号带回给引擎，它会剔除后重发，避免一个坏账号拖垮整批人
            return SendReceipt.fail("企微返回 errcode=" + errcode + " " + errmsg, invalidUsers);
        } catch (Exception e) {
            // 关键：抛出去！（不要吞掉后返回 success）
            // 引擎会整批判失败 + 释放限流键，且异常不会冒到你的定时任务里
            throw new RuntimeException("企微接口调用失败：" + e.getMessage(), e);
        }
    }
}
```

> 两条铁律：**坏账号要放进回执**（否则一个人拖垮整批）；**异常要抛出来**（否则这批人永远发不出去还不知道）。

**② 限流存储**（Redis，一行搞定）：

```java
public class RedisDailyLimitStore implements DailyLimitStore {
    // Spring 版本
    public boolean tryOccupy(String key, String value, int ttlSeconds) {
        return Boolean.TRUE.equals(redisTemplate.opsForValue()
                .setIfAbsent(key, value, Duration.ofSeconds(ttlSeconds)));   // SET NX EX
    }
    public void release(String key) { redisTemplate.delete(key); }
    public boolean isOccupied(String key) { return Boolean.TRUE.equals(redisTemplate.hasKey(key)); }
}
```

**③ 收件人数据源**（SQL 参考，注意两处"不要"）：

```sql
SELECT u.user_id AS userId, u.nick_name AS respUserName, u.user_name AS account,
       u.web_com_id AS webComId, d.dept_name AS deptName,
       /* 角色：给 GATE-ROLE 闸门用，逗号分隔 */
       (SELECT GROUP_CONCAT(r.role_key)  FROM sys_user_role ur
          JOIN sys_role r ON r.role_id = ur.role_id WHERE ur.user_id = u.user_id) AS roleKeys,
       (SELECT GROUP_CONCAT(r.role_name) FROM sys_user_role ur
          JOIN sys_role r ON r.role_id = ur.role_id WHERE ur.user_id = u.user_id) AS roleNames,
       COUNT(*) AS assetTotal,
       SUM(CASE WHEN a.check_status = 0 THEN 1 ELSE 0 END) AS assetPending
FROM eam_stocktaking_item i
JOIN sys_user u ON u.user_id = i.resp_user_id          -- ① 只按用户ID精确匹配，不要按姓名兜底
LEFT JOIN sys_dept d ON d.dept_id = u.dept_id
LEFT JOIN eam_asset a ON a.asset_id = i.asset_id
WHERE i.plan_id = #{planId}
GROUP BY u.user_id, u.nick_name, u.user_name, u.web_com_id, d.dept_name
-- ② 不要写 HAVING assetPending > 0：已盘完的人也要返回，由引擎判 SKIP 并写明原因
```

**④ 测试模式配置**（先放系统参数表，值就是一行文本）：

```
键：stocktaking.notify.testmode
值：testMode=true|accounts=你的工号|setBy=你的名字|setAt=2026-09-22 10:00
```

> 格式规则（v1.0.1 起）：键顺序随便、大小写随便；但只要**写错**（比如把 `testMode` 拼错、值写成 `1`），
> 引擎一律按"测试模式开着但白名单为空"处理 = **一条都不发**，并在日志里打 `配置非空但解析不到 testMode 开关键`。
> 这是故意的：配置写错的代价必须是"少发"，绝不能是"发给全员"。

### 3.4 沙箱四步验证（每步都有明确的"看什么"）

**步骤 1：先演练，不真发**

```java
List<NotifyResult> preview = engine.notify(plan, NotifyType.REMIND, LocalDate.now(), true);
```

看什么：
- 返回里每个人是 `PREVIEW`（正常）还是 `SKIP`（被拦，`reason` 会写明原因）
- 日志有 `[PREVIEW] 结果=演练`
- **企微那边一定没有新消息**（演练不发）

通过标准：能拿到文案、能看到谁会被发，且**企微零消息**。

**步骤 2：测试模式真发，只发给你自己**

```java
engine.sendDailyRemind(plan, LocalDate.now());
```

看什么（按顺序）：

| 日志关键字 | 说明 | 是否正常 |
|---|---|---|
| `[GATE-STATUS] 结果=通过` | 状态闸门过了 | 正常 |
| `[GATE-HOLIDAY] 结果=跳过` | 今天是周末/节假日 | **如果今天确实放假，属正常**；否则查日历 |
| `[GATE-WINDOW] 结果=跳过` | 今天不在"开始~截止"之间 | 查计划日期 |
| `[TEST-MODE] 状态=开启` + `条件=...` | 测试模式已识别到你的白名单 | 正常 |
| `[GATE-LIST] 结果=成功 可投递责任人=1` | 清单取到 1 个人 | 正常 |
| `[SEND] 结果=成功` | 企微真发出去了 | 正常 |
| `[SUMMARY] 汇总[发送=1 跳过=0 失败=0]` | 最终结果 | 正常 |

通过标准：**手机企微真的收到那条盘点提醒**，且 `[SUMMARY] 发送=1 失败=0`。

**步骤 3：同一天再跑一次（验一天一条）**

再执行一遍 `engine.sendDailyRemind(plan, LocalDate.now())`。

看什么：`[DAY-LIMIT] 结果=跳过 ... 一天一条`，且 `[SUMMARY] 发送=0 跳过=1`。

通过标准：**手机只收到 1 条**（第二条没发）。

**步骤 4：故意让企微失败，看它自愈（这一步最能证明修复有效）**

把企微 `secret` 改错一个字（或把网络断开），再跑一次。
（前提：先把 Redis 里 `stocktaking:notice:daily:{你的userId}:{今天}` 这个键删掉，模拟"今天还没发过"）

看什么，**三件事必须同时成立**：

1. 日志出现 `[SEND] 结果=异常` 或 `[SEND] 结果=失败 ... 发送接口异常`
2. `[SUMMARY] 汇总[... 失败=1 ...]` —— **是"失败"，不是"跳过"**（这是 P0-1 修复）
3. Redis 里那个限流键**已经没了**（`redis-cli get stocktaking:notice:daily:...` 返回 nil）—— 这是 P0-2 修复，允许当天补发

然后**把 secret 改回来，再跑一次**：应该能正常发出。

通过标准：三件事全成立，且修好后能补发成功。

## 4. S3：脏数据演练（生产上迟早会遇到）

用测试模式对着自己造以下几种人，逐个看结果：

| 造的数据 | 预期结果 | 日志/返回里的证据 |
|---|---|---|
| 已盘完的人（待盘点 0） | 不发 | `decision=SKIP`，`gateNode=BENEFICIARY`，reason 含"无待盘点资产" |
| 没有企微号的人 | 不发，且**不会发给别人** | reason 含"无可用企业微信账号" |
| 企微号写错/离职（不可用账号） | 整批先失败 → 剔除这个人 → 其余人重发成功 | `[SEND] 结果=部分失败 ... 剔除后重发人数=N`；该人 reason 含"账号不可用" |
| 两个人配了同一个企微号 | 只调用一次、只发给一个号 | `[SEND] 结果=注意 ... 重复企微号（数据脏）` |
| 清单里一个人都没有 | 整批不发 | reason 含"无责任人数据……**或全部资产已盘完**" |
| 某个人角色不在 `notifyRoles` 里 | 不发这个人，其余人照发 | `decision=SKIP`，`gateNode=GATE-ROLE` |

通过标准：每一行都对得上，且**没有一条"该发的人被漏发"**。

## 5. S4：生产灰度（不要一把梭）

| 步骤 | 操作 | 观察窗口 | 必须看到的 |
|---|---|---|---|
| ① 预演 | 生产环境跑 `dryRun=true` 的诊断接口 | 立即 | 目标人数对得上业务预期（差太多就先别上线） |
| ② 金丝雀 | 测试模式白名单 = 财务 1~2 人，真实发送 | 1 天 | 留痕表有数据、本人确认收到、`失败=0` |
| ③ 小范围 | 白名单扩到 1 个部门 | 1 天 | 失败率 < 1%；失败的人 Redis 键已释放（能补发） |
| ④ 全量 | 关闭测试模式（把配置改成 `testMode=false` 或清空） | 持续 | 每日核对 `[SUMMARY]` 与留痕表 |

**回滚方案**（任何一步发现异常，30 秒内可退）：

1. **立即止血**：把测试模式配置改成 `testMode=true|accounts=财务负责人工号`（白名单收窄到 1 个人），引擎下一轮就只发这一个人；
2. **完全停发**：把配置改成 `testMode=true`（无白名单）—— 引擎按 fail-closed **一条都不发**；
3. **不影响已发**：已经发出去的消息无法撤回，但不会再有新增。

> 为什么回滚这么简单？因为引擎是**每次执行时读取配置**，不需要重启服务。

## 6. 日志关键字速查表（排错只看这几行）

| 你看到的 | 含义 | 该干什么 |
|---|---|---|
| `[SUMMARY] 汇总[发送=0 跳过=2 失败=0]` | 全部被正常拦下 | 看这 2 条各自的 `gateNode`，确认拦截理由合理 |
| `[SUMMARY] ... 失败=N`（N>0） | 真出问题了 | 搜 `[SEND] 结果=失败`，看 `原因=` 后面的字 |
| `[SEND] 结果=异常` | 企微接口抛异常了 | 查网络/secret/企微服务状态；限流键已释放，修好可重跑 |
| `[DAY-LIMIT] 结果=跳过` | 这个人今天已经发过了 | 正常（一天一条是硬承诺）；想重测先删 Redis 键 |
| `[TEST-MODE] 配置非空但解析不到 testMode 开关键` | **你的配置写错了**，已自动按"一条不发"处理 | 按 `testMode=true|accounts=...` 格式重配 |
| `[AUDIT] 原因=发送留痕落库失败` | 消息发了，但留痕表没写成功 | 查数据库；消息本身没受影响 |
| `[SEND] 结果=注意 ... 重复企微号` | 有人共用账号（数据脏） | 推动业务改数据，不影响发送 |
